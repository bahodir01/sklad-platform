# Архитектура платформы складского учёта

**Версия:** 1.1 · **Основание:** ТЗ, редакция от 17.07.2026 (правки по подписи и модели заявок)
**Стек:** Python 3.12 / FastAPI · React 18 + TypeScript · PostgreSQL 16 · Docker

> **Внимание, вопрос трассируемости.** В шапке правленого ТЗ по-прежнему стоит «Версия документа: 1.1» — та же, что у исходной редакции, при изменившемся содержании (убран `react-signature-canvas`, добавлен `requests.writeoff_id`, переписан §4.4). Документ имеет статус «Согласовано: бумажная подпись», то есть на руках у сторон существуют две разные бумаги с одним номером версии. **Рекомендую поднять до 1.2 и внести правки в лист изменений** до того, как ТЗ уйдёт в разработку.

## 1. Ключевые архитектурные решения (ADR)

Прежде чем описывать структуру — четыре решения, которые определяют весь остальной дизайн.

### ADR-1. Остаток — это проекция журнала движений, а не хранимое поле

**Требование ТЗ (§5.1):** «Остаток товара на складе = сумма всех движений. Прямое редактирование остатка запрещено».

**Решение.** `stock_movements` — единственный источник правды (append-only, записи не редактируются и не удаляются). Поверх него — денормализованная таблица `stock_balances (product_id, warehouse_id, qty)`, которая обновляется **в той же транзакции**, что и вставка движения.

**Почему не считать `SUM(qty)` на лету:** при 1500+ сотрудниках и годах истории агрегат по миллионам строк не уложится в требуемые ≤500 мс (§9). Почему не только кэш-таблица: она может разойтись с историей. Комбинация даёт скорость чтения и проверяемость.

**Гарантия целостности:**
- Все проверки остатка (`перемещение`, `выдача`) делают `SELECT ... FOR UPDATE` по строке `stock_balances` → сериализация конкурентных списаний, невозможность уйти в минус при гонке.
- CHECK-constraint `qty >= 0` на `stock_balances` — последний рубеж на уровне БД.
- Регламентная задача-ревизор (Celery beat, ночью) сверяет `stock_balances` с `SUM(stock_movements)` и алертит при расхождении.

### ADR-2. Заявка — документ-основание, расход — проводка (по правке ТЗ)

**Решение заказчика.** `requests` и `writeoffs` остаются отдельными таблицами. Связь: `requests.writeoff_id`, заполняется **в момент выдачи**. До нажатия «Выдано» проводки не существует.

```
Сотрудник                              Завсклад
─────────                              ────────
requests (draft)
   │ confirm()
   ▼
requests (to_print) ──► очередь ──► print() ──► requests (printed)
                                                    │ issue()
                                                    ▼
                                            writeoffs + writeoff_items  ← проводка
                                            stock_movements (−qty)      ← списание
                                            requests.writeoff_id = ?    ← связка
                                            requests (issued)
```

**Почему это работает** (первоначально предлагалось слияние в одну таблицу — вариант заказчика лучше):
- Порча и брак не тащат бессмысленные для них поля `printed_at`, `pdf_url`, статусы `draft`/`to_print`. При слиянии они были бы всегда `NULL` — мусор в схеме.
- Разделение честно отражает две разные роли: заявка — процессный документ сотрудника, `writeoff` — учётная проводка склада. Все списания (выдача, порча, брак) единообразно лежат в одной таблице.

**Что обязано быть, иначе модель разъедется:**

```sql
ALTER TABLE requests ADD CONSTRAINT issued_iff_posted
  CHECK ((status = 'issued') = (writeoff_id IS NOT NULL));   -- выдана ⟺ есть проводка
ALTER TABLE requests ADD CONSTRAINT uq_writeoff UNIQUE (writeoff_id);
CREATE INDEX ON requests (writeoff_id);   -- обратный поиск: проводка → заявка → бумага
```

Инвариант `issued ⟺ writeoff_id IS NOT NULL` — главная защита этой схемы. Без него возможна заявка в статусе «Выдан» без проводки (товар отдали, учёт не знает) или проводка без заявки (списание без основания). Оба состояния — дыра в учёте, которую при двух таблицах не поймать иначе.

### ADR-2a. Два номера: на бумаге — номер заявки

**Следствие ADR-2, не описанное в ТЗ.** В момент печати `writeoff` ещё не существует, значит на PDF-бланке физически может стоять только **номер заявки**. §6.3 называет колонку очереди «номер расхода» — это терминологическая неточность: до выдачи расхода нет.

Итого две независимые серии нумерации (у `writeoffs` своя, потому что порча/брак заявки не имеют). Бухгалтерия получает бумагу с номером заявки, в учёте списание лежит под номером проводки.

**Решение:** реестр выданных документов (§6.4) показывает **оба номера**, поиск работает по любому из них. Иначе по бумажке из папки бухгалтера через полгода не найти проводку.

### ADR-3. Списание — строго на переходе `printed → issued`

**Требование ТЗ (§6.2):** «Товар списывается ТОЛЬКО при переходе в статус "Выдан"».

**Решение.** Движение `stock_movements` создаётся **исключительно** сервисом при вызове `POST /requests/{id}/issue`, одновременно с рождением проводки (ADR-2). Статусы `draft`/`to_print`/`printed` остаток не трогают. Резервирования нет (ТЗ его не требует) — это осознанный компромисс: два сотрудника могут заявить один и тот же последний товар, и второй получит ошибку «недостаточно на складе» в момент выдачи. Если заказчик захочет резерв — добавляется поле `qty_reserved` в `stock_balances` без ломки схемы.

### ADR-4. Электронной подписи нет нигде (закрыто правкой ТЗ)

Ранее §2.1 указывал `react-signature-canvas`, что противоречило §6 («подпись рукописная на бумаге, а не электронная»). **Заказчик убрал библиотеку из стека**, заменив строкой «Печатные формы → WeasyPrint → PDF-бланки для печати и подписи от руки».

Единственный юридический артефакт выдачи — бумажный бланк с рукописной подписью, физически передаваемый в бухгалтерию (§6.4). В системе подписи не существует ни в каком виде. ЭП остаётся будущим расширением (§9), в текущей версии не проектируется.

### Решения по конкретным полям

| Поле | Решение | Обоснование |
|---|---|---|
| Денежные суммы | `NUMERIC(18,2)`, никогда `float` | UZS-суммы в сотни тысяч; float даст ошибки округления в балансе кассы |
| Количество товара | `NUMERIC(14,3)` | Единицы измерения включают кг и л (§3.1) — дробные количества обязательны |
| `notification_items.qty_purchased` | **не хранится**, считается из `acquisition_items` | ТЗ помечает поле «расч.»; хранение создало бы второй источник правды и риск рассинхронизации при удалении приобретения |
| `cash_desks.balance` | хранится, обновляется в TX с `FOR UPDATE` | То же обоснование, что ADR-1: скорость + защита от гонки при контроле «не уходить в минус» |
| `writeoffs.employee_id` | `NULL` разрешён | §3.4: при типах «Порча»/«Брак» сотрудник не указывается. Целостность обеспечивает CHECK, сверяющий `expense_type.requires_employee` |
| `requests.writeoff_id` | `NULL` до выдачи + CHECK `issued ⟺ NOT NULL` | ADR-2: проводка рождается только на «Выдано». Без CHECK возможна выдача без списания |
| Удаление справочников | только `status = archived` | §3.1: «запрет физического удаления, если единица используется» |

### Индексы под требование ≤500 мс

```sql
-- горячий путь: остатки и история
CREATE UNIQUE INDEX ON stock_balances (product_id, warehouse_id);
CREATE INDEX ON stock_movements (product_id, warehouse_id, created_at DESC);
CREATE INDEX ON stock_movements (doc_type, doc_id);          -- переход к документу-основанию
-- очередь «К печати» — самый частый запрос админ-панели

CREATE INDEX ON requests (employee_id, created_at DESC);      -- «мои заявки» у сотрудника
-- отчёт ДДС (§8.2): фильтр по категории + периоду обязателен
CREATE INDEX ON money_expense (cash_desk_id, date DESC);
CREATE INDEX ON money_expense (employee_id, date DESC);
-- недокупленное по уведомлениям (§8.1.2)
CREATE INDEX ON acquisition_items (product_id);
CREATE INDEX ON acquisitions (notification_id);
```

## 5. Бизнес-правила: где именно они живут

Каждое правило ТЗ реализуется **в сервисном слое внутри транзакции** и дублируется constraint-ом в БД там, где это возможно.

### 5.1. Контроль перезакупки (§4.2) — `documents/service.py`

```
create_acquisition(notification_id, items):
    BEGIN
    SELECT ... FROM notification_items
        WHERE notification_id = ? FOR UPDATE       # блокируем строки уведомления
    для каждой строки:
        purchased = SUM(acquisition_items.qty) по этому notification+product
        remaining = qty_requested - purchased
        IF item.qty > remaining:
            RAISE DomainError(
              'Товар "Бумага A4": остаток к приобретению 10 шт, '
              'невозможно приобрести 15 шт')          # формат ошибки из §4.2
    INSERT acquisition + items
    ledger.post(+qty, doc_type='acquisition')        # приход на склад (§4.2)
    IF все строки закрыты: notification.status = 'closed'   # автозакрытие (§4.1)
    COMMIT
```

`FOR UPDATE` на строках уведомления обязателен: без него два параллельных приобретения по одному уведомлению оба прочитают `remaining = 10` и оба пройдут проверку — классический TOCTOU, приводящий к перезакупке, которую ТЗ запрещает.

### 5.2. Единая точка записи движений — `stock/ledger.py`

Единственный модуль во всей системе, которому разрешено писать в `stock_movements` и `stock_balances`. Все документы вызывают только его:

```
ledger.post(product_id, warehouse_id, qty: ±, doc_type, doc_id, session)
    → SELECT qty FROM stock_balances WHERE (product, wh) FOR UPDATE
    → IF balance + qty < 0: RAISE InsufficientStock(product, available)
    → INSERT stock_movements(...)
    → UPDATE stock_balances SET qty = qty + ?
```

| Операция | Вызовы ledger |
|---|---|
| Приобретение (§4.2) | `post(+qty, 'acquisition')` на склад поступления |
| Перемещение (§4.3) | `post(−qty, 'transfer', from_wh)` + `post(+qty, 'transfer', to_wh)` — две записи, как требует §4.3 |
| Выдача сотруднику (§6.2) | `post(−qty, 'writeoff')` — **только** при `issue()`, вместе с созданием проводки |
| Порча / брак (§4.4) | `post(−qty, 'writeoff')` — сразу при создании: заявки нет, печати нет, подписи нет |

### 5.3. Статусная машина выдачи (§6.2) — `issuance/service.py`

```
draft ──confirm()──► to_print ──print()──► printed ──issue()──► issued
 │                      │                     │                    │
сотрудник           попадает в            генерируется PDF,   создаётся writeoff,
заполняет           очередь завсклада      сотрудник ставит    ledger.post(−qty),
                    (бейдж-счётчик)        подпись на бумаге   writeoff_id проставлен
```

Переходы только вперёд и только соответствующей ролью; `issue()` в обход печати отклоняется — §6.3 требует, чтобы «Выдано» была доступна после печати.

**Переход `issue()` — самое опасное место в системе.** Он необратим (товар физически отдан) и делает четыре записи, которые обязаны случиться все вместе или ни одна:

```
issue(request_id):
    BEGIN
    writeoff = INSERT writeoffs(...) RETURNING id       # проводка рождается ПЕРВОЙ
    INSERT writeoff_items ← из request_items
    для каждой строки: ledger.post(−qty, 'writeoff', writeoff.id)   # может упасть: нет остатка

    UPDATE requests                                     # статус и связка — ОДНИМ оператором
       SET status='issued', issued_at=now(), writeoff_id=:writeoff_id
     WHERE id=:id AND status='printed'                  # условие ВНУТРИ UPDATE, не в IF
    IF rowcount = 0: RAISE Conflict                     # → ROLLBACK, проводка откатится с ним
    COMMIT
```

**Почему именно такой порядок — не переставлять.** Инвариант INV-2 (`status='issued'` ⟺ `writeoff_id IS NOT NULL`) реализован как `CHECK`, а `CHECK` в PostgreSQL проверяется **немедленно на каждом операторе** и не может быть `DEFERRABLE` (это доступно только UNIQUE/PK/FK/EXCLUDE). Поэтому «сначала поставить статус, потом проставить `writeoff_id` вторым UPDATE» роняет транзакцию на первом же операторе — в момент между ними состояние «выдано, но проводки нет» нарушает CHECK. Обе колонки обязаны меняться одним оператором.

Проводка создаётся спекулятивно, до проверки условия. Это безопасно: всё в одной транзакции, при `rowcount = 0` откатывается вместе с ней — осиротевших `writeoffs` не остаётся.

Ослаблять INV-2 до `DEFERRABLE INITIALLY DEFERRED` constraint trigger ради сохранения прежнего порядка — плохой размен: внутри транзакции состояние «выдано без проводки» стало бы легальным, а это ровно та дыра, от которой инвариант и защищает.

Защита от двойного списания — **в условии `WHERE ... AND status='printed'`**, а не в предварительной проверке `if status == 'printed'`. Проверка-и-действие двумя запросами оставляет окно между ними: два параллельных клика «Выдано» оба прочитают `printed`, оба пройдут проверку и создадут две проводки. Условный UPDATE атомарен — второй получит `rowcount = 0`. Плюс `Idempotency-Key` на эндпоинте отсекает ретрай сети до входа в транзакцию.

### 5.4. Контроль баланса кассы (§7.3) — `cash/service.py`

```
create_expense(...):
    BEGIN
    SELECT balance FROM cash_desks WHERE id = ? FOR UPDATE
    IF balance < amount: RAISE InsufficientFunds       # ← режим настраивается, см. §10
    проверить наличие прикреплённого чека              # §7.3: чек обязателен
    INSERT money_expense; UPDATE cash_desks SET balance = balance - amount
    COMMIT
```

Касса определяется **сервером** из `current_user.category`, а не приходит с клиента (§7.3: «Касса — авто»). Иначе учитель мог бы списать из кассы работников, подделав тело запроса.

**Правила уровня API:**

- **Идемпотентность:** `POST /requests/{id}/issue` и `POST /cash/income` принимают заголовок `Idempotency-Key`. Двойной клик по «Выдано» на медленной сети не должен списать товар дважды — это необратимая порча учёта.
- **Ошибки:** доменные исключения централизованно маппятся в `422` с телом `{code, message, details}`, где `message` — готовый русский текст для тостера (формат из §4.2).
- **Пагинация:** обязательна на всех списках (§9), keyset-пагинация на `stock_movements` — offset на длинной истории деградирует.

## 7. Frontend

**Организация — feature-sliced:** `app → pages → features → entities → shared`, импорт только вниз по слоям.

**Разделение состояния (§2.1):**
- **TanStack Query** — всё, что пришло с сервера: остатки, документы, отчёты. Инвалидация по ключам: `issue()` инвалидирует `['stock','balances']`, `['writeoffs','to_print']` и метрики дашборда одновременно.
- **Zustand** — только локальный UI: открытые диалоги, черновики фильтров, состояние сайдбара.

**Маршруты по ролям:**

```
/login
admin:            /dashboard  /to-print(бейдж)  /notifications  /acquisitions
                  /transfers  /writeoffs  /stock  /cash  /reports/*  /catalog/*
teacher|worker:   /my/requests  /my/requests/new  /my/expenses  /my/expenses/new
```

**Бейдж «К печати» (§6.3).** Счётчик обновляется через `refetchInterval: 30s` на лёгком эндпоинте `GET /writeoffs/count?status=to_print`. Polling, а не WebSocket: задержка до 30 секунд для очереди печати бизнес-критичной не является, а WS на 1500 пользователей — это отдельная инфраструктура (sticky sessions, Redis pub/sub, переподключения) без соразмерной пользы. Если заказчик потребует мгновенности — переход на SSE точечный, без ломки архитектуры.

**Формы:** React Hook Form + Zod, схемы генерируются из OpenAPI (`openapi-typescript`) — типы фронта не расходятся с бэкендом при изменении API.

## 9. Безопасность, аудит, эксплуатация

**Аутентификация.** JWT: access 15 мин (в памяти JS), refresh 30 дней (httpOnly+Secure+SameSite cookie). Access не в localStorage — XSS-кража токена. Пароли — Argon2id. Refresh-ротация с детекцией переиспользования.

**Аудит (§9).** Middleware пишет в `audit_log` каждое изменяющее действие: `user_id, action, entity, entity_id, payload_diff, ip, timestamp`. Таблица append-only, доступ на чтение — только admin.

**Файлы (§9).** MinIO, отдельные бакеты `receipts` / `documents`. Валидация по magic bytes (не по расширению), лимит 10 МБ, whitelist `jpg/png/pdf`. Отдача — presigned URL с TTL 5 мин, бакеты приватные: чек — финансовый документ, публичная ссылка недопустима.

**Наблюдаемость.** Структурные JSON-логи с `request_id`, `/health` + `/ready` для оркестратора, Prometheus-метрики (latency по эндпоинтам — прямой контроль требования ≤500 мс).

**Тестирование.** pytest + testcontainers (реальный PostgreSQL — половина логики живёт в транзакциях и constraint-ах, на SQLite она непроверяема). Обязательное покрытие: перезакупка, конкурентное списание последнего товара, уход кассы в минус, двойной `issue()`.

## 10. Открытые вопросы (требуют решения заказчика)

Закрыто правкой правке ТЗ: противоречие по электронной подписи (ADR-4) и структура заявка/расход (ADR-2).

| # | Вопрос | Влияние на архитектуру | Рекомендация |
|---|---|---|---|
| 1 | Шаблоны печатных форм | **Блокирует этап 3** (Jinja-шаблоны PDF) | Запросить сейчас — нужны до старта М4 |
| 2 | Недостаток средств: блокировка или предупреждение? | **Решать ДО миграции.** Ранее здесь было сказано «флаг конфигурации, схема не меняется» — **это неверно**: INV-8 реализован как `CHECK (balance >= 0)` в DDL, и никакой флаг приложения его не обойдёт. Режим предупреждения потребует миграции с удалением CHECK | Жёсткая блокировка: §9 называет «уход баланса в минус» защищаемым инвариантом |
| 3 | Кто ставит статус «Напечатан» | Влияет на статусную машину | Вручную завскладом: открытие PDF ≠ факт печати (мог не выйти из принтера) |

**Терминологический хвост правки (не блокирует).** §6.2 и §6.3 всё ещё говорят «документ-расход проходит статусы» и «номер расхода» в очереди, хотя по §10 в правленой редакции статусы принадлежат заявке, а расход появляется только на «Выдано». Структурно модель однозначна, расходится только словарь. Стоит поправить при следующей ревизии, чтобы разработчик не искал несуществующую сущность.
