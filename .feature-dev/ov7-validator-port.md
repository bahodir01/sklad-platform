# ОВ-7 · Порт валидатора контракта на SQLAlchemy 2.0 + Pydantic v2

**Файл:** `.claude/skills/database-schema-design/assets/contract_validator_sqlalchemy.py`
**Оригинал** `contract_validator.py` (Django + DRF) **не тронут** — он остаётся для
Django-проектов, где плагин используется штатно. Оба файла лежат рядом, стек выбирается
запуском нужного.

Зависимостей нет: чистый `ast`, ни SQLAlchemy, ни Pydantic импортировать не требуется.

## Как запускать

```bash
python contract_validator_sqlalchemy.py contract.json models.py [schemas.py ...]
```

- **exit 0** — код сходится со словарём;
- **exit 1** — расхождения, каждое отдельной строкой с тегом (`[table]`, `[attribute]`,
  `[type]`, `[fk]`, `[nullable]`, `[unique]`, `[index]`, `[default]`, `[extra]`,
  `[api]`, `[unmatched]`);
- **exit 2** — неверный вызов.

**Каждый** файл после контракта сканируется на оба вида классов: mapped-классы опознаются по
`__tablename__`, схемы — по `BaseModel`/`model_config`. Поэтому модульная раскладка
(`models.py` + `schemas.py` в каждом модуле, `03-architecture.md` §171) работает просто
перечислением всех файлов; порядок не важен. Проверка схем остаётся опциональной по содержимому:
если ни одного Pydantic-класса не найдено, отрабатывают только проверки моделей.

Шаг 4 пайплайна `feature-development` вызывает его так:

```bash
python .claude/skills/database-schema-design/assets/contract_validator_sqlalchemy.py \
    .feature-dev/02-contract.json \
    backend/app/modules/*/models.py backend/app/core/audit.py \
    backend/app/modules/*/schemas.py
```

⚠️ Перечислять надо **все** файлы с моделями. `AuditLog` живёт не в `modules/*/models.py`,
а в `backend/app/core/audit.py` — при вызове только по глобу `modules/*/models.py` валидатор
честно репортит `[table] 'audit_log' ... has no mapped class`, что выглядит как расхождение,
а на деле — недоданный файл. Глоб в команде шага 4 должен покрывать `core/` тоже.

## Что проверяет

### Модели (обязательный аргумент)

| Проверка | Детали |
|---|---|
| Таблица | Класс ищется по `__tablename__`, **не по имени класса** — ключевое отличие от Django-оригинала, где идентичность модели = имя класса. Классы без `__tablename__` (сам `Base`, миксины) пропускаются. |
| Атрибут | Каждый атрибут словаря должен быть `mapped_column`. Если имя занято `relationship()` — отдельное сообщение, а не «поле отсутствует». |
| Тип | Строгое сравнение нормализованных строк: `String(32)`, `Numeric(14, 3)`, `DateTime(timezone=True)`, `SAEnum(CatalogStatus, name='catalog_status')`, `JSONB`, `INET`. Пробелы и вид кавычек не значат; проза в скобках (`INET (postgresql.INET)`) и хвост после `·` отбрасываются. При совпадении семейства, но разных параметрах (`String(32)` → `String(64)`) сообщение это отмечает. |
| ForeignKey | Цель и `ondelete`, из `ForeignKey(...)` в колонке **и** из табличного `ForeignKeyConstraint(...)` в `__table_args__` (составной FK `writeoffs`). Ловится потерянный FK, лишний FK, чужая цель, отсутствующий/несовпавший `ondelete`. |
| nullable | Сравнивается **эффективная** nullability по правилам самого SQLAlchemy: явный `nullable=` > `primary_key=True` > подсказка `Mapped[T \| None]`. Дополнительно ловится противоречие `Mapped[str]` + `nullable=True` — аннотация врёт. |
| unique | `unique=True`, `primary_key=True` или **одноколоночный** `UniqueConstraint`. Составной `UniqueConstraint("product_id", "warehouse_id")` намеренно **не** делает колонки уникальными (иначе `stock_balances` давал бы ложняк). Обратная проверка тоже есть: `unique=True` в модели при пустой ячейке словаря — расхождение. |
| index | Только позитивное направление: словарь требует индекс → он должен быть (`index=True`, PK, unique, или упоминание колонки в `Index(...)`/`UniqueConstraint(...)` из `__table_args__`, включая выражения `text("created_at DESC")`). Обратное направление не проверяется — см. «Не покрыто». |
| default | Наличие `default=`/`server_default=` в обе стороны + сравнение нормализованного значения: `now()` ⟷ `func.now()`, `active (server_default='active')` ⟷ `text("'active'")`, `True (server_default=true)` ⟷ `text("true")`. |
| Лишнее | Колонки модели, которых нет в словаре, и целые таблицы, которых нет в контракте. |

### Pydantic-схемы (опционально)

Вместо одного DRF-сериализатора с `fields` у нас раздельные схемы. Правило — строгое «тогда
и только тогда»:

| Схема | Флаг контракта |
|---|---|
| `XxxCreate` | `api.create` |
| `XxxUpdate` | `api.update` |
| `XxxRead` | `api.get_single` |
| `XxxList` | `api.get_index` |

Поля резолвятся **транзитивно через локальные базовые классы**: `UnitCreate(UnitBase)` отвечает
за поля, унаследованные от `UnitBase`.

**Аналог запрета `fields = "__all__"`:** схема с `model_config = ConfigDict(from_attributes=True)`,
не объявившая ни одного поля (ни своего, ни через базовый класс), зеркалит модель целиком и
физически не может соблюдать пофайловые флаги → расхождение.

### Соответствие имён схема → таблица

Правило явное, описано в докстринге модуля. Первое сработавшее выигрывает:

1. `__contract_table__ = "warehouses"` на классе — всегда побеждает. `__contract_table__ = None`
   исключает класс из проверки (для схем без таблицы: `TokenCreate`, `LoginCreate`).
2. Отбросить суффикс → искать **mapped-класс с таким именем** → взять его `__tablename__`.
   `WarehouseCreate` → класс `Warehouse` → `warehouses`. Основное правило; вывозит нерегулярные
   имена: `MoneyIncomeCreate` → `MoneyIncome` → `money_income`.
3. Отбросить суффикс → snake_case → имя таблицы контракта напрямую, затем наивные множественные
   (`+s`, `+es`, `y→ies`).

Класс без одного из четырёх суффиксов схемой запроса/ответа не считается и молча пропускается
(там живут `WarehouseBase` и прочие миксины). Класс **с** суффиксом, но не сопоставленный ни одним
правилом, — **не угадывается**, а сообщается как `[unmatched]` и роняет гейт: схема, которую
гейт не может сопоставить, — это схема, которую гейт не проверяет.

Отдушина: `__contract_extra_fields__ = {"items"}` разрешает поля, которых нет в словаре
(вложенные payload'ы, вычисляемые значения).

Модели извлечены из `02-database.md` §6 (512 строк) во временный `.py`.
В `backend/` ничего не создавалось и не менялось — там работает другой агент.

**Против `02-contract.json` (22 таблицы, 128 атрибутов) — 1 расхождение:**

```
CONTRACT MISMATCH — 1 issue(s):
  - [index] products.name: dictionary requires an index ('True (trgm, поиск по названию)'),
    model declares none
```

**Это не ложняк валидатора — это настоящее расхождение, и оно уже задокументировано агентом БД**
в `02-database.md` §11:

> Индекс на `products.name` под `ILIKE` помечен в словаре как `trgm`-кандидат, но **не создан**:
> §4 не описывает поиск по названию как access pattern. Добавится отдельной ревизией, если
> появится требование.

То есть словарь говорит «индекс есть», код говорит «индекса нет» — ровно тот случай, ради
которого гейт и ставился. **Ослаблять валидатор под это я не стал**: чинить надо словарь
(проставить `db_index` пустым для `products.name`) либо создать индекс. Решение за владельцем
контракта — это ОВ, а не баг порта.

На копии контракта с этой единственной согласованной ячейкой (`db_index=""` у `products.name`)
валидатор проходит **зелёным** по всем 22 таблицам и 128 атрибутам, включая рукописные
Pydantic-схемы для `warehouses` / `units` / `money_income`:


## Бонус: прогон на реальном `backend/`

Пока шёл порт, соседний агент выложил `backend/` в модульной раскладке. Валидатор прогнан и по
нему (**в `backend/` ничего не создавалось и не менялось** — только чтение):

```bash
python ... 02-contract.json backend/app/modules/*/models.py backend/app/core/audit.py \
                            backend/app/modules/*/schemas.py
```
```
CONTRACT MISMATCH — 2 issue(s):
  - [index] products.name: dictionary requires an index ('True (trgm, ...)'), model declares none
  - [api] schema 'UserCreate' declares field 'password', which is not an attribute of 'users'
```

Оба — настоящие, оба требуют решения человека, ни одно не является багом валидатора:

1. `products.name` — тот же ОВ, что и выше.
2. **`UserCreate.password`** — новая находка. В словаре у `users` есть `password_hash`, а схема
   принимает `password`: write-only вход, который сервис хеширует. Расхождение реальное — словарь
   про этот атрибут API не знает вообще. Варианты: завести в словаре строку `password`
   (`create=true`, всё остальное `—`) либо, если это сознательно «не атрибут таблицы», пометить
   `__contract_extra_fields__ = {"password"}` в `UserCreate`. Решение за владельцем контракта.

Это ровно тот класс расхождений, ради которого гейт ставился: схема принимает поле, которого
словарь не описывает.

## Важный нюанс про `nullable`

В ТЗ на порт значилось «убери `nullable` → должно ловиться». Буквально это выполнимо, но было бы
**неверно**: в SQLAlchemy 2.0 nullability выводится из `Mapped[T]` / `Mapped[T | None]`, и снятие
`nullable=False` с колонки `Mapped[str]` не меняет ни схему БД, ни поведение — это форматирование,
а не расхождение. Валидатор, ругающийся на это, обучил бы команду глушить гейт.

Поэтому сравнивается **эффективная** nullability (явный kwarg > PK > аннотация). Реальные поломки
этого класса ловятся все: флип значения (#5), снятие `nullable` с расширением аннотации (#4),
и противоречие kwarg'а с аннотацией (#6). Если политика проекта — требовать явный `nullable=`
всегда, это отдельная проверка стиля, и её место в линтере, а не в контрактном гейте.

## Что осталось непокрытым по сравнению с Django-оригиналом

Оригинал этого тоже не покрывал (порт **строго шире** по проверкам), но перечисляю честно:

1. **Обратное направление по индексам.** Индекс в модели, не отмеченный в словаре, не считается
   расхождением. Составные индексы (`AP-5`, `AP-8`) штатно накрывают колонки, которые словарь
   индивидуально не помечает, — строгая проверка давала бы поток ложняков. Позитивное направление
   (словарь требует → должно быть) работает.
2. **Тип не проверяется, если он не написан явно** в `mapped_column()` (`mapped_column(ForeignKey(...))`
   без типа — легальная форма, тип берётся из аннотации). Такие колонки попадают в блок `NOTES`,
   который печатается, но гейт не роняет. В текущих моделях таких нет.
3. **Прочие поля словаря не проверяются:** `editable`, `filter`, `other_validations`, весь блок
   `frontend` (`input_type`, `required`, `max`, `disabled`, `table_view`), `legacy`. Оригинал их
   тоже игнорировал. `frontend`-блок — предмет гейта фронтенда, не бэкенда.
4. **`CheckConstraint` не сверяется** со словарём: в словаре инварианты живут прозой в
   `other_validations` (`"qty > 0"`, `INV-1…INV-9`), машинно сопоставлять их с SQL-выражениями
   без формализации ячейки нельзя. Проверка INV — за тестами (шаг QA), не за AST-гейтом.
5. **`__table_args__` разбирается только на `Index` / `UniqueConstraint` / `ForeignKeyConstraint`.**
   `postgresql_where`, `postgresql_using`, порядок колонок и направление сортировки в индексе
   не сверяются — словарь их и не формализует (пишет прозой: `partial: WHERE status = 'to_print'`).
6. **Типы Pydantic-полей не проверяются** — только присутствие/отсутствие по флагам. Оригинал для
   DRF делал ровно то же (смотрел на список имён в `fields`).
7. **Динамика игнорируется** (как и в оригинале): поля, собранные циклом/`type()`, миксины из
   других модулей, `create_model()`. Парсер статический. Для сгенерированного агентом кода это
   не проблема.
8. **Типы полей Pydantic не сверяются с типами колонок** (`code: int` в `WarehouseCreate` при
   `String(32)` в модели пройдёт). Оригинал для DRF тоже этого не делал. Потенциальная доработка,
   если шаг 4 начнёт ловить такие расхождения на ревью.
