# 10 · Frontend, финал — два пробела (ФИО сотрудника · UI порчи/брака)

**Вход:** живой backend `http://127.0.0.1:8000`, готовые этапы 1–6 (`05a`, `06`). Типы перегенерированы с живого бэка (`npm run api:types`) — в ответах заявок появились `employee_full_name` + `employee_category`.
**Правило соблюдено:** код только в `frontend/`. Ни одного выдуманного поля — все payload/колонки из OpenAPI/контракта. Этапы 1–6 дополнены, не переписаны.

## Пробел 1 — ФИО сотрудника + категория (§6.3/§6.4)

Бэк теперь отдаёт `employee_full_name` (JOIN на users, тот же приём, что в ДДС) и `employee_category` в `RequestList` (`GET /requests?status=to_print`, `/requests/my`) и `RegistryRow` (`GET /requests/registry`). Раньше очередь и реестр рисовали «Сотрудник #id» (D-4/Q-1 закрыты).

**Добавлено:**
- `entities/request/ui/EmployeeCell.tsx` — переиспользуемый компонент: реальное ФИО + бейдж категории (`CategoryBadge`: Учитель = info/синий, Работник = muted/серый; цвет никогда не единственный сигнал, §11). Фолбэк на `Сотрудник #id`, если `employee_full_name` пришло null (историческая запись).

**Изменено (замена `Сотрудник #id`):**
- `pages/requests/ToPrintPage.tsx` — колонка «Сотрудник» очереди «К печати».
- `pages/requests/RegistryPage.tsx` — колонка «Сотрудник» реестра выданных.

Отдельного экрана «деталь заявки» в UI нет (в этапах 1–6 не строился — `RequestRead` используется только в мутациях), поэтому менять там нечего. Отмечено в отклонениях.

## Пробел 2 — UI прямого списания порча/брак (§4.4)

`POST /writeoffs` (admin) создаёт списание порча/брак БЕЗ заявки: тип расхода с `requires_employee=false`, `employee_id` не указывается (INV-4, обязан быть NULL), списывает немедленно (`ledger.post(−qty)`). Q-5/D-5 закрыты.

**Добавлено:**
- `entities/writeoff/model/types.ts` — `WriteoffCreate/Read/ItemCreate` из schema.d.ts.
- `entities/writeoff/api/mutations.ts` — `useCreateWriteoff()` → `POST /writeoffs`, инвалидирует `['stock']` + `['reports']`.
- `entities/expense-type/api/queries.ts` — `useActiveExpenseTypes()`.
- `entities/expense-type/ui/ExpenseTypeSelect.tsx` — селект типа расхода с флагом `requiresEmployeeFalseOnly`: показывает только `requires_employee=false` (Порча/Брак). «Выдача» физически не выбирается (фильтр по справочнику на клиенте — API фильтра не даёт, К-C).
- `features/documents/writeoff-form/writeoff.schema.ts` — Zod: `date`, `warehouse_id`, `expense_type_id`, строки `product_id`+`qty`+`reason`. `employee_id` в схему не входит.
- `pages/documents/WriteoffsPage.tsx` — полностраничная форма (шаблон `TransfersPage`): склад + тип расхода (фильтр Порча/Брак) + строки товар/кол-во/причина. Успех → тост `WOFF-xxxxxx`, сброс формы. Ошибки — тостером через `applyApiError` (готовый русский текст с бэка, не переписывается).

**Роутинг/навигация:**
- `shared/config/routes.ts` — `writeoffs: "/writeoffs"`.
- `app/router.tsx` — маршрут под `<RequireRole admin>`.
- `app/layouts/nav-config.tsx` — пункт «Списание (порча/брак)» в разделе «Документы» (admin).

## (а) Отклонения

- **Экран «деталь заявки» в замену `Сотрудник #id` не менялся — его в UI нет.** В этапах 1–6 отдельный `RequestDetailDialog`/страница детали не строились (заявка видна списком: очередь, реестр, «Мои заявки»). `RequestRead` используется только в мутациях. Заменены обе точки, где реально рисовался «Сотрудник #id»: очередь и реестр. Если нужен отдельный экран детали заявки — это новый экран, а не правка существующего (вне «дополни, не переписывай»).
- **Списка проведённых списаний нет** — как у приобретений/перемещений (D-2), в API только `POST /writeoffs`, GET-журнала нет. Экран = форма проведения.
- **Фильтр `requires_employee` — на клиенте.** API `GET /expense-types` его не принимает (К-C, подтверждено живьём: только `status`). Отфильтровал загруженный `status=active` список. Приемлемо: справочник типов расхода крошечный (2 записи).
- **Опциональные списки-просмотры приобретений/перемещений не делал** — ТЗ явно не требует, не приоритет (указано в задаче), в API нет GET.

## (б) Вопросы по ТЗ

- **QF-1.** Нужен ли отдельный экран/диалог «деталь заявки» (с позициями и ФИО)? Сейчас его нет — заявка живёт только в списках. Если да — это новый экран.
- **QF-2.** Категория сотрудника — бейджи «Учитель»/«Работник» (по `UserCategory teacher|worker`). Подписи верны? (Совпадает с вопросом Q-7 про подписи касс.)
- **QF-3.** У прямого списания порча/брак журнала проведённых нет (нет GET). Нужен ли реестр списаний на бэке? (Аналог Q-4 для приобретений/перемещений.)
