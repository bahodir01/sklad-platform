# Спецификация: Telegram-бот вместо публичных форм (закрывает ОВ-12)

**Основание:** согласовано с заказчиком 21.07.2026. Заменяет отложенную идею публичных веб-форм (ОВ-12) на Telegram-бота. **Логика системы не меняется** — бот лишь заменяет собой веб-форму как канал ввода для сотрудников, которые больше не заходят в систему через браузер.

---

## 1. Область действия

**Сценарий A (подтверждён явно).** Бот создаёт обычную заявку/расход — точно так же, как раньше это делала форма «Мои заявки» / «Мои расходы». Никакого мгновенного списания в обход завсклада. Вся статусная машина фичи 13 (draft→to_issue→issued→signed→submitted) остаётся как есть; списание товара по-прежнему происходит только на «Выдать» у завсклада.

**Через бота:**
1. **Заявка на товар** — эквивалент `POST /requests` (создание) + `POST /requests/{id}/confirm`. Итог — заявка в статусе `to_issue`, дальше обычный путь через журнал «Выдачи товара».
2. **Расход денег** — эквивалент формы «Мои расходы»: вид расхода, сумма, описание, **фото чека** (Telegram отдаёт фото файлом — скачивается и кладётся в MinIO/локальный фолбэк как `receipt_url`, как при обычной загрузке). Касса определяется сервером по категории пользователя (SV-6), как сейчас.

**НЕ через бота:** ничего административного (справочники, кассы, отчёты, пользователи) — бот доступен только ролям teacher/worker.

## 2. Привязка Telegram-аккаунта к пользователю (по телефону)

**Схема (новая миграция `0004_telegram`):**
- `users.phone` — varchar(20), nullable, unique (частичный индекс `WHERE phone IS NOT NULL`). Формат хранения — нормализованный (только цифры с `+`, напр. `+998901234567`).
- `users.telegram_chat_id` — bigint, nullable, unique (частичный индекс). Заполняется ботом при успешной привязке, не через API создания пользователя.

**Поток привязки:**
1. Админ при создании/правке пользователя (модуль «Пользователи») вносит номер телефона.
2. Учитель открывает бота → `/start` → бот показывает **одну reply-кнопку** «📱 Отправить номер телефона» (Telegram `request_contact`, отправляется автоматически, без ввода).
3. Бот получает `contact.phone_number` → нормализует → ищет `users.phone` с совпадением → при находке пишет `telegram_chat_id`, отвечает «Здравствуйте, {full_name}, вы авторизованы как {role_label}».
4. Не найден → «Ваш номер не найден в системе. Обратитесь к администратору.» Повторная попытка разрешена (не блокируется).
5. Уже привязанный пользователь, пишущий `/start` снова, — просто получает приветствие без повторной привязки.

**Один Telegram-аккаунт — один пользователь.** Один пользователь — один Telegram-аккаунт (уникальность в обе стороны, обе колонки unique).

## 3. Диалог создания заявки на товар (гибрид: текст + кнопка-подтверждение)

Через reply-клавиатуру бот предлагает два действия в главном меню: **«📦 Заявка на товар»** и **«💵 Расход денег»**.

**Заявка на товар:**
1. Бот: «Выберите склад» — inline-кнопки **только складов с `allows_issuance=true`** (SV-9, тот же список, что фильтрует веб-форма).
2. Бот: «Напишите название товара». Учитель печатает как есть (`бумага`).
3. **Поиск товара — трёхступенчатый** (учитель может писать на любом языке — русском, узбекском, английском; номенклатура хранится по-русски, см. §3a):
   1. **Подстрока** — `ILIKE %текст%` по активным товарам. Бесплатно, мгновенно, покрывает большинство случаев (написано по-русски или совпадает частично).
   2. **Ничего не нашлось → ИИ-поиск смысла.** Сервис отправляет текст учителя и список активных товаров (id+название, тех же, что видны на выбранном складе) языковой модели с запросом «какие из этих товаров могут иметь в виду», получает ранжированный список кандидатов. ИИ **только предлагает**, не выбирает — так же, как и подстрочный поиск, результат идёт кнопками.
   3. **И это не дало результата (или ИИ недоступен/ошибка/таймаут) → «Показать весь список»** — постраничный список всей номенклатуры кнопками, учитель находит визуально. Всегда доступна как ручная альтернатива на любом шаге.
   - Результат любого из шагов 1-2 — **до 5 совпадений inline-кнопками** + кнопка «Показать весь список».
   - 1 совпадение — можно сразу подтверждать (не заставлять жать кнопку ради единственного варианта, но подтверждение всё равно есть в итоговом резюме шага 6).
4. Учитель выбирает товар кнопкой → бот: «Сколько?» → учитель пишет число.
   - Валидация формата на стороне бота (число, > 0) до отправки на сервер — не гонять заведомо невалидный ввод в API.
5. Бот: «Причина получения?» → свободный текст.
6. Бот показывает **резюме** (склад, товар, количество, причина) + кнопки **«✅ Отправить» / «❌ Отмена»**.
7. «Отправить» → `POST /requests` + `POST /requests/{id}/confirm` от имени этого пользователя → бот отвечает номером заявки («Заявка REQ-000123 отправлена, ждите выдачи»). Отказ сервера (422 и т.п.) — текст ошибки сервера как есть, диалог не рвётся, можно начать заново.

**Множественные строки в одной заявке** — вне scope первой версии (веб-форма это умеет, бот пока не обязан). Учитель, которому нужно несколько позиций, оформляет несколько заявок или пишет боту заново — отметить как известное упрощение.

### 3a. ИИ-поиск товара по смыслу (мультиязычность)

**Проблема.** Номенклатура хранится по-русски (ТЗ §9). Учитель может написать `paper`, `qog'oz`, латиницей или кириллицей — прямой текстовый поиск ничего не найдёт. Переводить названия каждого товара заранее — ненадёжно и требует ручного сопровождения справочника.

**Решение — семантическое сопоставление, не перевод.** Сервису передаётся сырой текст учителя **и** реальный список товаров (id+название) из номенклатуры — модель ищет совпадение по смыслу в контексте настоящих названий, а не переводит слово в вакууме. Модель никогда не создаёт и не выбирает сущность — только предлагает кандидатов, которые идут кнопками (то же свойство безопасности, что у обычного поиска: ошибка ИИ = кандидат не в списке или не выбран, а не неверное списание).

**Реализация:**
- Отдельный сервис `app/shared/ai_search.py` (или модуль `modules/ai`) с функцией `suggest_products(query: str, candidates: list[Product]) -> list[ProductMatch]`.
- Провайдер — Anthropic API (Claude, модель попроще/подешевле — задача мелкая, классификация по короткому списку). Промпт: текст пользователя + JSON-список `{id, name}` активных товаров → просим вернуть id подходящих (0-5) с кратким обоснованием необязательно.
- Вызывается **только когда шаг 1 (подстрока) дал ноль результатов** — экономит запросы.
- Таймаут (напр. 5с) и любая ошибка API → тихий переход к шагу 3 (список), не роняет диалог с ботом.
- Ключ и включённость — в едином экране «Интеграции» (см. §5а).

## 4. Диалог расхода денег

1. Бот: «Выберите вид расхода» — inline-кнопки из `expense_categories` (активные).
2. Бот: «Сумма в UZS?» → число.
3. Бот: «Опишите расход» → текст.
4. Бот: «Пришлите фото чека» → ждёт `photo`. Не-фото ввод — переспрашивает.
5. Резюме + «Отправить/Отмена».
6. «Отправить»: скачивает фото у Telegram (`getFile` → байты) → загружает как `receipt_url` (тот же путь, что multipart-загрузка в вебе) → `POST /cash/expenses`. Ответ сервера (в т.ч. `InsufficientFunds`) — прямым текстом пользователю.

## 5а. Экран «Интеграции» (админ-панель) — единое место для внешних ключей

**Схема:** таблица `integration_settings`, **одна строка на тип интеграции** (`kind` — `telegram` | `ai_search`), не две отдельные таблицы:
`id`, `kind` (varchar, unique), `secret_encrypted` (bytea/text, шифруется симметрично ключом из `.env` — **не хранится в открытом виде**), `display_name` (varchar, напр. bot username или имя модели), `is_enabled` (bool), `updated_by` → users, `updated_at`.

**Эндпоинты (admin-only), общие для обоих типов:**
- `GET /admin/integrations` — список обеих интеграций: `kind`, `display_name`, `is_enabled`, `updated_at`, **секрет никогда не возвращается** (маска вида `123456:AAE••••1234` / `sk-ant-••••ab12`).
- `PUT /admin/integrations/{kind}` — принимает новый секрет:
  - `telegram`: перед сохранением проверяется вызовом Telegram `getMe` — невалидный токен не сохраняется, ошибка сразу видна; при успехе `display_name` = username бота из ответа; поднимает/перезапускает polling-процесс.
  - `ai_search`: лёгкая проверка ключа (тестовый вызов) перед сохранением.
- `POST /admin/integrations/{kind}/disable` — гасит интеграцию (`is_enabled=false`); для telegram — останавливает polling; для ai_search — поиск товара просто пропускает шаг 2 (сразу на список).

**UI:** один экран «Интеграции» в разделе «Администрирование» — две карточки (Telegram-бот, ИИ-поиск), в каждой: поле ввода секрета (password-type), кнопка «Сохранить и проверить», статус (включена/выключена + display_name), кнопка «Отключить».

## 6. Технический запуск бота

**Режим — polling, не webhook.** Локальная dev-среда без публичного HTTPS-адреса (нет Docker/reverse proxy наружу) — webhook недостижим без доп. инфраструктуры (ngrok и т.п.). Polling работает без публичного адреса и достаточен для масштаба школы. Решение фиксировано для этого проекта; webhook можно рассмотреть отдельно при выходе на прод-хостинг с доменом.

**Процесс:** отдельный долгоживущий процесс (не встроен в FastAPI worker, не Celery-задача — это постоянно слушающий цикл). Реализация — `aiogram` (asyncio, хорошо ложится на существующий async-стек SQLAlchemy). Управление стартом/остановом — через тот же процесс, что читает `integration_settings` (либо систему сигналов, либо перечитывание настроек по таймеру — решает исполнитель).

**Библиотека:** `aiogram>=3` — добавить в `pyproject.toml`.

## 7. Инженерные ограничения

- Схема заморожена и накатана — очередная миграция `0004` (поверх 0003, НЕ трогать прежние).
- Токен **никогда** не логируется, не возвращается клиенту в открытом виде.
- Бот действует **от имени привязанного пользователя** — все бизнес-правила (INV/SV, RBAC) применяются так же, как при обычном API-вызове; бот — это ещё один клиент API, не отдельный привилегированный путь.
- Все создаваемые ботом сущности проходят те же сервисы (`IssuanceService`, `CashService`), что и веб — никакой дублирующей бизнес-логики.
- pytest: тесты на привязку (совпадение/несовпадение телефона), на сборку заявки/расхода через сервисный слой с теми же данными, что дал бы диалог бота.
