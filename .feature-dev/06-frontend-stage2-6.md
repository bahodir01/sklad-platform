# 06 · Frontend, ЭТАПЫ 2–6 (Заявки · Документы · Кассы · Отчёты)

**Вход:** живой backend `http://127.0.0.1:8000`, `02-contract.json`, `05a-frontend-architecture.md`, готовый этап 1 и начатые `pages/requests` + `features/requests`.
**Стек не менялся:** React 18 + TS · shadcn/ui · TanStack Query + Zustand · RHF + Zod · типы из OpenAPI. Русский UI, UZS, ru-RU.
**Правило соблюдено:** код только в `frontend/`. Типы перегенерированы с живого бэка (`npm run api:types`). Ни одного выдуманного поля — все payload/колонки из контракта и OpenAPI.

## 1. Что сделано (экраны)

### М4 Заявки (было начато — завершено и подключено к роутеру)
- **Мои заявки** (`pages/requests/MyRequestsPage`, teacher/worker) — список `GET /requests/my`, создание (`RequestCreateDialog`, склад только `allows_issuance`), подтверждение draft→to_print.
- **Очередь «К печати»** (`ToPrintPage`, admin) — по макету: 3 KPI, объединённая таблица `to_print`+`printed`, кнопка **Печать** (→`print`), кнопка **Выдано** активна **только после печати** (ADR-3, `disabled` у to_print), пакетная печать.
- **Реестр выданных** (`RegistryPage`, admin) — оба номера (заявки + проводки).
- **Бейдж «К печати»** в sidebar — `GET /requests/count?status=to_print`, `refetchInterval 30с`, запрашивается только у admin.

### М2 Документы (admin) — новое
- **Уведомления** (`pages/documents/NotificationsPage`): список с фильтром по статусу; **создание** (`NotificationCreateDialog`: `date`, `warehouse_id`, `body_text`, `division_name`, `comment`, строки `product_id`+`qty_requested`); **деталь** (`NotificationDetailDialog`: шапка + строки с остатком к приобретению `qty_requested/qty_purchased/qty_remaining` + **печать PDF** `GET /notifications/{id}/pdf` blob'ом в новую вкладку).
- **Приобретения** (`AcquisitionsPage` + `AcquisitionCreateDialog`): на основании уведомления. Строки прогружаются из остатка к приобретению (`qty_remaining`), количество по умолчанию = остаток, цена необязательна. Ошибку перезакупа §4.2 (`insufficient`/`SV-1`) показывает тостером (`applyApiError` → `message`).
- **Перемещения** (`TransfersPage` + `transfer.schema`): полностраничная форма источник→получатель + строки; получатель обязан отличаться от источника.

### М5 Кассы — новое
- **Кассы** (`pages/cash/CashPage`, admin): балансы обеих касс (`GET /cash/desks`, KPI-карточки) + форма прихода (`IncomeForm`, `POST /cash/income`).
- **Мои расходы** (`MyExpensesPage`, teacher/worker): форма расхода (`ExpenseForm`, **multipart с обязательным чеком-файлом** `POST /cash/expenses`: вид/сумма/описание/дата/чек) + список своих расходов. **Кассу сотруднику не показываем** — её определяет сервер по категории (SV-6); в форме её нет.

### М6 Отчёты (admin) — новое
- `pages/reports/ReportsPage` — 4 таба, активный рендерится один (не бьём бэкенд всеми запросами разом):
  - **Остатки** — фильтр по складу, экспорт xlsx/pdf.
  - **Недокупленное** — фильтр по датам, экспорт.
  - **История движений** — keyset вперёд/назад по курсору, знаковое qty, фильтры doc_type + даты, экспорт.
  - **ДДС** — **обязательный фильтр по категории (кассе)** (AP-8): без категории отчёт не запрашивается и экспорт заблокирован; KPI приход/расход/итог + балансы касс; экспорт.
- Экспорт (`ExportButtons`) — `GET {report}?format=xlsx|pdf`, качается blob'ом (Authorization в памяти).

### Каркас
- Роутинг переписан по ролям (`app/router.tsx`): `<RequireRole admin>` на М2/М4-очередь/реестр/кассы-приход/отчёты; `<RequireRole teacher|worker>` на «Мои заявки»/«Мои расходы». Сотрудник админских экранов не видит (→ `/403`).
- `RoleHome` (`/`): admin → «К печати», сотрудник → «Мои заявки».
- Sidebar (`AppSidebar`, `nav-config`) — пункты фильтруются по роли, живой бейдж очереди. Мёртвые заглушки убраны.
- Новые селекты: `CashDeskSelect`, `ExpenseCategorySelect`.

## 4. Отклонения (сообщаю, не «чиню»)

| # | Отклонение | Причина |
|---|---|---|
| **D-1** | **Регенерация `schema.d.ts` уронила корневые алиасы `UserRole`/`CatalogStatus`** — плоский вывод `openapi-typescript` их не создаёт, а этап 1 их импортировал по имени. | Добавил `shared/api/model-types.ts` (руками, `components["schemas"][...]`) и перенаправил 4 файла этапа 1 + новые. Это устойчиво к перегенерации, но **потребовало трогать файлы этапа 1**. Иначе `npm run api:types` ломает сборку. |
| **D-2** | Приобретения и перемещения — **без GET-списка** (в API только POST). Приобретения = список открытых уведомлений с действием «Провести»; Перемещения = полностраничная форма без журнала. | В контракте/роутере нет `GET /acquisitions`/`GET /transfers`. |
| **D-3** | Уведомление создаётся как **`draft`**, а в `in_progress` переходит лишь после первой закупки (проверено в `documents/service.py`). Экран «Приобретения» по умолчанию показывает **все, кроме `closed`**, а не только `in_progress` — иначе свежие уведомления, которые как раз надо закупать, были бы скрыты. | Лайфцикл статуса на бэке. |
| **D-4** | ФИО сотрудника в очереди/реестре — **`Сотрудник #id`** (нет `GET /users`, М7 не построен). При этом ДДС отдаёт `employee_name` — там ФИО есть. | Нет справочника пользователей. См. Q-1. |
| **D-5** | Убраны мёртвые пункты меню: **Дашборд** (нет эндпоинтов метрик), **Расходы товара/writeoffs** (этап 4), **Склад › Остатки/Движения** (покрыто «Отчётами»). | Не строить заглушки без данных. См. Q-2/Q-5. |
| **D-6** | Фильтры/пагинация отчётов — в **локальном стейте**, не в URL (в отличие от справочников). История движений — keyset вперёд/назад курсором. | Отчёты — админская аналитика; шаринг ссылкой не требуется. |

## 5. ВОПРОСЫ по ТЗ (явным списком)

- **Q-1.** ФИО сотрудника в очереди «К печати» и реестре не резолвится — нет `GET /users` (М7). Нужен ли эндпоинт справочника пользователей, чтобы показывать ФИО вместо `Сотрудник #id`? (ДДС уже отдаёт `employee_name` — рассинхрон между модулями.)
- **Q-2.** Нужен ли сотруднику экран остатков склада? `GET /stock/balances` — любая роль, но экрана нет (М3 вне списка «доделать»). Строить `/stock` или остатки только в «Отчётах» (admin)?
- **Q-3.** Свежесозданное уведомление, требующее закупки, имеет статус `draft` (не `in_progress`). Так задумано, или создание должно сразу ставить `in_progress`? От этого зависит семантика «открытых» уведомлений на экране приобретений.
- **Q-4.** У приобретений и перемещений нет GET-списка — журнал проведённых документов не предполагается (только создание)? Или его нужно добавить на бэке?
- **Q-5.** Прямое списание порча/брак (`POST /writeoffs`, admin) — это этап 4 и вне текущего scope? Экран не строил.
- **Q-6.** Асинхронный экспорт больших отчётов (`POST /reports/export` + Celery) — не подключал, использую только синхронный `GET ?format=`. Порог «маленький/большой» должен решать клиент; нужен ли async-путь в UI сейчас?
- **Q-7.** ДДС: категория (`teacher|worker`) — обязательный фильтр (реализовано). Правильные ли подписи касс «Касса учителей / Касса работников»?

## 6. Что мешало

- **curl на Windows/Git-Bash калечил inline-JSON с кириллицей** (`-d '{...}'`) → FastAPI `«error parsing the body»`. Лечится записью тела в файл и `--data-binary @file`. **К фронту отношения не имеет** — `fetch` шлёт `JSON.stringify` (UTF-8) корректно; это артефакт ручного теста.
- Регенерация `schema.d.ts` стёрла алиасы этапа 1 (D-1) — пришлось разбираться, почему вдруг «сломался» готовый этап, и добавлять `model-types.ts`.
